# 自建 Agent Runtime 方案对照《AI Agents in Depth》评审

日期：2026-09-01  
评审对象：`docs/架构/自建智能体运行时设计.md`（上游：`docs/架构/智能体工具框架设计.md`）  
对照文本：图灵《AI Agents in Depth》（`ai-agent-book`，引言至第十章）  
结论：**设计理念与本书高度同向，是一份合格的生产级执行协议；主要缺口在验证层、上下文工程细节和评估闭环，而不是控制面 / 执行面拆分本身。**

---

## 1. 结论先行

本书的核心公式是 **Agent = LLM + 上下文 + 工具**，生产视角再写成：

> **Agent = Model + Harness**  
> Harness = 上下文 + 工具 + 约束 + 验证 + 纠正

Smart Chat 方案把这件事拆成两层：

| 本书用语 | 方案用语 | 实际职责 |
| --- | --- | --- |
| Model | Provider Adapter | 生成文本或工具意图 |
| Harness 中的约束 / 策略 / 编排 | Control Plane + Policy Snapshot | 为什么执行、由谁执行、允许看什么、允许做什么 |
| Harness 中的循环、工具执行、恢复 | Runtime Plane | 如何逐轮调用模型和工具，并可靠暂停、恢复、结束 |
| Loop / Graph 工程中的持久控制面 | PostgreSQL 状态机 + TaskEnvelope | 目标、配额、审批、检查点、终止条件放在模型之外 |

这不是偏离本书，而是把第一章的 Harness 和 LoopX 思路落到聊天室产品上：模型提出候选动作，系统批准、执行、记账。方案明确「自建的是运行时和治理协议，不是训练模型」，也符合第七章「能靠 Harness 解决的，先不要后训练」。

整体判断：

1. **理念正确。** 控制面冻结观察空间与动作空间，执行面只消费快照；模型不能自行扩大权限。这正是本书反复强调的「接口由系统定义，而不是由模型声称」。
2. **约束和纠正写得很完整。** 租约、Turn 边界恢复、幂等键、结果未知则停止、协作式取消、MCP schema digest、凭据不进任务包，都与第四、五章的生产级 Harness 一致。
3. **验证偏弱。** 本书认为生产级 Agent 的重心已经从「能做事」转到「可靠地做事」，而「可靠」三件套里，方案对约束、纠正着墨充分，对验证（独立于模型的完成判定、服务端真值、Sidecar）着墨不足。
4. **上下文工程还停在「可冻结、可压缩」，尚未落到第二章的运行时形状。** 缺 KV Cache 友好的静态前缀、Agent 状态栏、Skill / 工具渐进式披露。
5. **没有评估闭环。** 第六章把评估视为 Harness 的验证功能；方案有可观测性指标，没有「模型 + Harness 组合体」的评测、模型替换实验和轨迹回归。

建议把方案定位从「可恢复的服务端 Agent Loop」再明确一步：

> 建设一个由 Smart Chat 控制面驱动、**可验证完成**、可暂停恢复、可审计、Provider 无关的服务端 Agent Loop；上下文按静态前缀 + 轨迹 + 状态栏组装，工具按需披露，评估与执行协议同步建设。

## 3. 设计理念是否符合本书

**符合。** 九条核心决策里，有八条可以直接在书中找到对应原则；剩下一条（第一阶段不做通用编码 Agent）是产品节奏选择，与本书「方向认同、节奏务实」不冲突，但会压低通用能力上限。

### 3.1 同向的理念

**1. 模型是马，Harness 是挽具。**  
第一章：模型越强，外围外壳越关键。方案把 Provider 降为「生成候选文本或工具意图」，Policy Engine 决定拒绝、执行或等待审批。这就是 Harness 隐喻的工程化：不是限制模型思考，而是不让思考直接变成世界状态。

**2. 观察空间和动作空间由系统定义。**  
第一章把上下文和工具比作 LLM 与世界的 ISA。方案用冻结的 `TaskEnvelope` 锁定 Agent、模型、Context、Skill、MCP、策略和预算；Runtime「不自行扩大上下文、权限或工具集合」。这是接口层的正确归属。

**3. 执行路径可以自主，权限路径必须确定。**  
第一章区分工作流与自主 Agent：路径可以由环境反馈动态生成，但必须有停止条件。方案的 Agent Loop 是标准 ReAct（思考 → 工具 → 观察），终止条件覆盖输出契约、Turn / Token / 费用 / 工具次数 / 墙钟、取消、权限撤销、租约丢失、审批等待。自主性被关在预算和策略里面，而不是关在提示词里。

**4. 安全不靠系统提示词。**  
第二、四、五章的分层防御：上下文层（来源隔离）+ 执行层（权限、沙箱、独立审查）。方案写明「Prompt injection 不能只靠系统提示词」「工具授权只依据 Policy Snapshot，不依据模型声称」「附件、网页和 MCP 返回值不得改变允许工具、host、预算或审批规则」。这是书中最硬的安全原则，方案写对了。

**5. 数据库是事实来源，队列只负责唤醒。**  
第四章事件驱动架构、第十章轨迹持久化、LoopX「把目标、门禁、配额、验证与终止条件放进模型和聊天之外的持久控制面」。方案选 PostgreSQL 驱动状态机、Turn 边界恢复、不追求请求级流续传，与「事件只在循环安全点被消费」一致。

**6. 多 Agent 用进程，不用隐式线程。**  
第十章：不共享上下文 ≈ 进程；子 Agent 返回结构化摘要而非全量轨迹；取消沿创建关系向下级联；稀缺资源是 token / 费用 / 并发。方案禁止 Runtime Loop 内隐式 subagent，由控制面创建父子 `AiRun` 和 DAG，Aggregator 只收结构化结果和 Artifact 引用。这是书中管理者模式的正确落地，而不是「多个角色共用一段对话历史」的假多 Agent。

**7. 先专用受控工具，再谈通用编码。**  
第一章和第四章：通用基础能力用于组合与探索，专用工具用于高风险和强业务规则。第五章则论证 Coding + 文件系统是通用 Agent 的技术底座，但同时给出致命三要素。方案 Phase 1–4 走受控工具和 MCP，Phase 5 才给独立 `CODE_RUNTIME`，并要求容器、非 root、默认断网、禁止 Docker socket。这是「节奏务实」：聊天和业务 Agent 先可靠，再打开通用动作空间。

### 3.2 需要校正的理念表述

方案把职责写成：

```text
Harness：为什么执行、由谁执行、允许看到什么、允许做什么。
Runtime：如何逐轮调用模型和工具，并可靠暂停、恢复和结束。
```

按本书，Runtime 里的循环、工具执行器、checkpoint、错误分类重试，本身就是 Harness 的一部分。控制面是 Loop / Graph 工程那一层，不是「Harness 的全部」。建议在文档里补一句，避免团队把 Runtime 理解成「纯模型循环、不含约束」：

> Smart Chat 的 Harness 跨两个平面：控制面负责任务契约与治理，Runtime 负责单次 Run 内的 ReAct、策略执行、验证钩子和恢复。二者共用同一套 Task / Event / Result 协议。外部 CLI Runtime 也必须遵守这套协议。

这一校正不影响模块拆分，只避免后继实现把 Policy Engine、outputContract 核验误放到「可选项」。

## 4. 与本书高度契合的设计

### 4.1 第一章：Harness 五要素中的「约束」和「纠正」

| 方案机制 | 本书原则 | 章节 |
| --- | --- | --- |
| 故障安全：能力默认关闭，第一阶段无 Shell / Git / 宿主文件系统 | 约束采用故障安全默认值，必须显式开放 | 第一、四章 |
| `AUTHORIZE_TOOLS → DENY / WAITING_APPROVAL / EXECUTE` | 模型提议，系统批准；不可逆操作走事前审批 | 第四、五章 |
| 错误先分类再重试：429/5xx 可退，内容过滤 / 非法请求不盲重试 | 检测：先分类，再计数；不可重试错误原样重试没有意义 | 第五章 |
| 租约丢失不得提交；`(runId, sequence)` 唯一 | 崩溃恢复与幂等；产品可靠性取决于每类错误是否有路径 | 第五、十章 |
| 取消是协作信号，已提交副作用必须披露、不假装回滚 | 幂等与取消语义；优雅终止在安全点响应 | 第四、十章 |
| `continuity = FULL \| REBUILT \| GAP` | 保持透明；无法精确续传时披露连续性 | 第一、五章 |
| 保护线：最大 Turn 12、写工具串行、租约 60s | 自主 Agent 必须有停止条件；每条恢复路径都要有上限 | 第一、五章 |

这些不是文档装饰，而是把「Demo 能跑」和「生产可靠」分开的那些机制。Phase 0 用无工具 Adapter 包装现有 `chat/completions`、验收「用户行为不变」，也符合第一章「保持简单：先不要增加复杂度」。

### 4.2 第二章 / 上游 Harness：上下文可选择、可版本化

上游 `智能体工具框架设计.md` 已经比 Runtime 文档更接近第二章：

- Context Block 分级、pinned 策略、工具调用与结果必须成对保留
- 超预算时外部化为 Artifact，不能静默丢弃安全策略
- Skill Bundle 按 `SKILL.md` + hash 冻结
- 压缩顺序：去重 → 摘要 → Artifact → 阻断

Runtime 方案继承了「冻结 Context Bundle、按 digest 重建输入、不依赖 Worker 内存中的消息数组」。这解决了第一章消融实验里「没有历史消息等于失忆、会重复已完成步骤」的问题，也满足 Sessionless 架构对轨迹序列化的要求（第五章）。

### 4.3 第四章：工具、MCP、幂等、异步安全点

| 方案机制 | 本书原则 |
| --- | --- |
| 工具带 `risk` 与 `idempotency` | 执行工具按风险分级；KEYED / NON_IDEMPOTENT 决定能否自动重放 |
| 默认幂等键 `runId:toolCallId:argumentsDigest` | 同一操作执行一次和多次对世界的影响相同 |
| MCP 写工具不支持幂等则 `tool.outcome_unknown` + `BLOCKED` | 非幂等操作不可就地盲重发，应回到预检 / 上层决策 |
| MCP 是工具来源不是权限来源；`schemaDigest` 漂移则拒绝 | 锁定服务器版本，拒绝静默更新；工具描述视为不可信输入 |
| `secretRef` 调用时解析，凭据不进 Envelope / 事件 / Turn | 最小权限凭证，绝不把 token 写入任务上下文 |
| 暂停发生在 Turn 边界，不从中断的 HTTP 流续传 | 事件只在循环安全点被消费；不在任意时刻插入新事件 |
| 不可信文件工具走独立容器、只读根、网络 allowlist | 沙箱 + 出口控制，打断致命三要素中的外传通道 |

「结果未知不得自动重放非幂等写」是方案里最像本书的一句话。许多自建 Loop 会在超时后直接重试，这正是第四章要避免的真实世界事件翻倍。

### 4.4 第五章：编码能力作为可选平面，而不是默认权限

方案没有把 Shell 塞进普通 Runtime Worker，而是预留独立 `CODE_RUNTIME` capability、每 Run 容器和 workspace。这同时满足：

- 第五章「应用层当作不可信，把不变量下沉到运行时强制执行」
- 致命三要素：普通聊天 Runtime 不应同时具备私有数据、不可信内容和随意外连
- 第一章 ACI：高风险能力用设计消除误用，而不是靠模型自觉

Phase 5 的验收（无法访问宿主文件系统、Docker socket、未批准网络；取消后无残留进程）可以直接当作本书护栏清单的产品化表述。

### 4.5 第十章 / Loop 工程：图编排而不是对话里的角色扮演

- 父 Run `WAITING_CHILDREN` + barrier + Aggregator：管理者模式
- 子 Run 独立 Envelope、租约、checkpoint、预算、工具账本：进程隔离
- 取消和预算向子任务传播：Go context 式级联
- 多维配额（全局 / 房间 / 用户 / Provider / Runtime / MCP）：第十章「资源与调度」
- 审批、确定性策略、Agent Loop 都是图上的节点：第一章 Graph 工程（Agent 循环、程序、人工审批组织成显式执行图）

「不在模型循环中启动隐式 subagent」避免了第十章批评的那种「看起来像多 Agent、其实只是同一段上下文里换了人设」的结构。

### 4.6 安全信任分层

方案的三级信任模型与书中「数据 / 输入信任 / 输出影响 / 跨会话」四类边界同构：

```text
不可信：用户消息、附件、Skill、模型输出、MCP 响应
受控：TaskEnvelope、Policy Snapshot、Tool Registry、Runtime Worker
高敏：Provider/MCP 凭据、管理员策略、业务数据库
```

Runtime 不收用户 Cookie、不用管理员库权限、Worker 低权限角色，对应第五章「把 Agent 降格为权限受限的主体，即便被策反也越不过雷池」。

## 5. 建议改进

按「不改就会在真实长任务上反复踩书中已写明的坑」排序。P0 建议写入 Runtime 方案正文；P1 可进 Phase 1–3 验收；P2 作为后续阶段，但不要在数据模型里堵死。

### P0-1. 补上「验证」：模型不能批准自己完成

**书中依据。** 第一章 Harness 五要素把验证定义为独立于模型自由文本的检查。第十章 LoopX：**模型可以提出「完成」，但不能批准自己的「完成」。** 第五章机票案例：政策事实必须来自服务端数据库，不能来自模型自报参数。

**方案现状。** 终止条件包括「模型返回满足输出契约的结果」，`outputContract` 有 TEXT / JSON / ARTIFACT_SET，但没有独立核验器。`RunResult.decisions` 和 `followups` 是执行面自己写的。Policy Engine 管工具许可以后，任务是否真的做完仍由同一个 Loop 说了算。

**建议。**

1. 在 Loop 中增加 `VERIFY_OUTPUT` 状态，放在 `FINALIZE` 之前。JSON 契约用 schema 校验；业务结果用只读查询对照数据库真值（订单是否已退、消息是否已发），不要信模型 summary。
2. 高风险或长程任务增加独立 Reviewer Run：不同模型家族、只看结构化证据和 Artifact，不看主模型思考文本。这是第四章提议者-审核者，不是再写一遍系统提示词。
3. `RunResult.status = COMPLETED` 只能由控制面在验证通过后投影；Runtime 最多申报 `PROPOSED_COMPLETE`。
4. 工具参数中的业务事实（金额、资源 ID、成员身份）以服务端查询为准，模型参数只作提示。Policy Engine 已有房间权限检查，应把这条写成硬规则。

这不是要把每个闲聊都变成双模型审批，而是让「完成」和「执行」分开。与现有 `WAITING_APPROVAL` 是同一家族：审批管副作用，验证管交付。

### P0-2. 把 BUILD_INPUT 写成第二章的上下文形状

**书中依据。** 第二章的地基是「静态前缀不变、轨迹只追加、动态状态放在末尾」。破坏前缀（系统提示词里塞时间戳、滑动窗口丢掉早期工具结果、中途改工具列表）会同时打爆 Prompt Cache 和 Agent 记忆。状态栏必须由代码维护，模型会无条件相信它。

**方案现状。** Runtime 说「由冻结 Context Bundle、已提交 Turn 和 Tool Result 确定性构建」，但没有规定：

- 哪些块构成跨 Turn 不变的静态前缀
- Skill / MCP schema 是前缀全量注入还是末尾按需追加
- 当前时间、已用 Turn / 费用 / 工具次数、审批等待、子任务进度放在哪里
- 压缩是否禁止滑动窗口、是否保持 tool 调用与结果配对

**建议。** 在 6.2 / 7.2 增加 `ModelInputLayout`：

```text
[静态前缀，跨 Turn 字节级稳定]
  系统策略 + Agent Persona + 冻结工具名索引 + 输出契约
[轨迹，只追加]
  已提交 Turn 与成对 Tool Result（大结果仅摘要 + artifactRef）
[按需追加，不回写前缀]
  本 Turn 新加载的 Skill 正文 / 工具完整 schema
[状态栏，每 Turn 由代码重写在末尾]
  now, turnIndex, budget remaining, tool counts, approval, children
```

状态栏字段用代码从 checkpoint 聚合，禁止再用一次 LLM 去「总结当前状态」。压缩失败连续 N 次熔断（第五章 Claude Code 的经验是 3 次），回退到人工或 `BLOCKED`，不要在压缩循环里空转。

上游 Context Planner 已有成对保留和 pinned block，应变成 Runtime 的硬约束，而不是 Planner 的偏好。

### P0-3. Skill / 工具：冻结版本，但不要整包塞进上下文

**书中依据。** 第二章 Skills 渐进式披露：启动时只给 name + description，需要时再读正文。第四章：5 个 MCP 服务器就可能吃掉数万 token；正确做法是索引 + 按需加载，动态 schema 追加在末尾以保住前缀缓存。能力表达还有三维决策：参数复杂度、变更频率、模型能力——弱模型需要结构化工具，强模型更适合 Skill + 通用执行器。

**方案现状。** 「固化 Skill Bundle hash」「MCP Gateway 校验 schemaDigest」对审计是对的，但容易被实现成「一次 Run 把批准过的 Skill 和工具 schema 全部放入 BUILD_INPUT」。Phase 3 验收「相同快照可确定性重建输入」也可能被理解成重建时必须全量回放。

**建议。** 把「冻结」和「注入」拆开：

| 冻结（审计 / 恢复） | 注入（模型可见） |
| --- | --- |
| Skill 目录 hash、每个 Skill 的 revision | 默认只注入目录（name + description） |
| 批准的 MCP schemaDigest 集合 | 默认只注入工具名索引；首次调用前再拉完整 schema |
| Policy Snapshot、预算、host allowlist | 始终注入，且 pinned |

加载过的 Skill / schema 写入 Turn 事件，恢复时只重建「已经加载过的集合」，未加载的保持索引。这样既满足 digest 可复现，又不把观察空间一次性撑满。弱模型 Agent 可以在 Policy 里声明 `toolDisclosure: "full"`，作为显式例外。

### P0-4. Policy Engine 之外增加 Sidecar，且只看结构化字段

**书中依据。** 同一上下文中的模型很难判断自己是否已被注入。第四章 Sidecar：与主流式输出并行，但门控单次工具调用；输入只有 `{tool, arguments}`，不看思考文本。第五章：推测性 UI 提示与安全检查并行，检查未通过只替换提示，无需回滚。

**方案现状。** 授权链是「工具版本 / Schema / capability / 房间权限 / 资源范围 / 审批 / 预算 / 幂等」。这覆盖了确定性约束，没有覆盖「参数表面合法、语义危险」的一层，例如看似只读的 MCP 查询把私钥当参数、或模型把注入指令复述成调用理由。

**建议。**

- `READ`：确定性策略通过即可执行
- `WRITE`：确定性策略 + 轻量 Sidecar（独立小模型，只看结构化调用）
- `DESTRUCTIVE` 或策略不确定：`WAITING_APPROVAL`
- Sidecar 延迟预算应写进保护线（例如 500ms）；超时的失败策略是升级审批，不是默认放行

不要让 Sidecar 读取用户原文或模型 thinking，否则提示注入会穿过话术通道。

### P1-1. 评估与执行协议一起做，而不是上线后再补

**书中依据。** 引言：没有评估就没有进步。第六章：评估对象是模型与 Harness 的组合体；用模型替换区分「模型不行」还是「Harness 不行」。第五章：用失败轨迹改进 Harness。

**方案现状。** Phase 0 有产品回归；第 13 节有延迟、费用、租约丢失等指标。缺少：

- 固定任务集上的轨迹金样（工具是否该调、是否越权、是否重复副作用）
- 同一 Harness 换模型、同一模型开关压缩 / 状态栏 / Sidecar 的消融
- 安全回归：提示注入夹在附件 / MCP 返回值 / Skill 正文中，断言策略不变、写工具不执行

**建议。** Phase 0 增加 `runtime/eval/`：至少 20 条房间任务（闲聊、只读查询、需审批写入、注入攻击、Worker 在 Turn 边界被杀）。验收从「不丢消息」扩展到「注入不能改变允许工具集」。没有这组测试，后续加 MCP 和多 Agent 无法判断是变好还是运气。

### P1-2. 流式连接要有空闲看门狗，不只是请求超时

**书中依据。** 第五章：最危险的失败不是断开，而是静默卡死；SDK 超时往往只覆盖建连。原则是「每个长连接都需要活性信号」。

**方案现状。** 有模型 120s 超时、工具 30s、租约续租，没有「N 毫秒没有新的 `text.delta` / `tool.arguments.delta` 就杀掉流」。租约续租可能让一个卡死的 Worker 一直占着 Run。

**建议。** Adapter 层独立 idle watchdog（例如 15–20s 无 delta），触发后按「请求超时且 Provider 无查询能力」处理：只读推理可重建并标 `REBUILT`，写工具已发出则 `outcome_unknown`。

### P1-3. BUILD_INPUT 必须标注来源，禁止把工具结果当成指令

**书中依据。** 第二章来源标记；第四章子 Agent 用 `[FROM_USER]` / `[TOOL_RESULT]`；第八章「原始网页、工具输出及其 LLM 摘要都属于不可信证据，不能当作指令执行」。

**方案现状。** 原则写了「数据内容与指令来源必须分层」，协议里 `ContentPart` 没有 `provenance`。实现时很容易把 MCP 返回值、网页正文、Skill 补充材料平铺进 user/assistant 消息。

**建议。** `ContentPart` 增加 `origin: "system_policy" | "user" | "skill" | "tool" | "mcp" | "memory" | "child_handoff"`。只有 `system_policy` 和经过 Planner 标记的用户目标具有指令效力。Skill 正文是「可加载的手册」，不是「可改权限的指令」。

### P1-4. 运行中事件：Turn 边界不只用于崩溃恢复

**书中依据。** 第四章三种策略：队列到下一个安全点、取消当前步、另起并行循环。聊天室产品必然出现「Agent 正在跑，用户又发了一句」。

**方案现状。** 暂停 / 审批 / 取消在 Run 级状态机上很完整，缺少 Run 内事件：追加用户消息、提高优先级、暂停当前工具。现在更像批处理 Worker，不像事件驱动助理。

**建议。** Phase 1 至少支持：新用户消息进入队列，在 Turn 边界注入为新的 user turn，不打断正在进行的模型 HTTP（与「不从流中续传」一致）；明确的取消仍用 AbortController。并行式「边跑边聊」放到更后，避免过早把一致性模型打复杂。

### P1-5. 并行只读工具的故障边界

**书中依据。** 第五章：故障只在同一批并行调用内传播，不上升到父级；独立调用继续。每个工具声明是否允许并发，默认否。

**方案现状。** 「同 Turn 并行只读工具：4，写工具：串行」是正确的保守默认，但没说其中一个 READ 失败时其余三个怎么办。

**建议。** ToolDefinition 增加 `concurrency: "forbidden" | "isolated"`。isolated 失败只标记自身；batch 内有依赖再级联。不要把一次搜索 404 变成整个 Turn 失败。

### P1-6. 用户记忆和检索结果是注入通道

**书中依据。** 第三章：跨会话记忆和 RAG 会把不可信文档送进眼睛。知识库投毒与网页注入同类。

**方案现状。** Context Planner 有 memory block，Runtime 未规定记忆 / RAG 的信任级。若房间摘要或用户记忆可被普通成员写入，等于给了持久化注入。

**建议。** memory / 检索块默认 `origin: "memory"`，无指令效力；写入记忆走独立审批或白名单抽取（固定 schema，不要把模型摘要直接当规则）。这可以放在 Phase 3，但数据模型现在就要有 origin。

### P2-1. 通用工具与专用工具的决策写进注册表

本书并不反对第一阶段不用 Shell，但反对把「专用工具白名单」当成终局。注册表应记录每个能力为什么不是 Skill + 通用执行器：安全、权限粒度、弱模型、还是暂时没沙箱。否则工具数量会按业务线线性膨胀，重新撞上第四章的选择过载和 KV Cache 问题。

### P2-2. 子任务预算应由 Planner 动态分配

第十章：Manager 应按复杂度分配步骤预算，并引导子 Agent 先规划再执行。方案给每个子 Run 独立预算是对的，但若只用全局默认 `maxTurns: 12`，简单检索和复杂分析会一样贵。建议 Envelope 允许父任务声明 `limits` 上限，Planner 在上限内分配，并在 handoff 里写明期望的工作顺序（规划 / 执行 / 自检）。

### P2-3. 协作工具、事件触发、用户沟通应进入工具体系

第四章五类工具：感知、执行、协作、事件触发、用户沟通。方案覆盖了感知 / 执行 / MCP，协作被上收到控制面 DAG（合理），但 Runtime 内没有 `spawn_subagent` 类协作工具，也没有「主动给用户发进度」的沟通工具。聊天室可以暂时靠 Result Projector 写消息，长任务会显得哑巴。建议 Phase 2 提供受控的 `notify_user`（权限与频率受限），Phase 4 再视需要把 spawn 做成控制面 API 而非模型随意调用。

### P2-4. 轨迹回流：为第八章留接口，不要现在做 Self-Harness

第八章：经验可写入知识、Prompt / Skill、程序、参数；安全机制不可被业务 Agent 修改。方案的事件账本已经是学习信号的原料。建议在验收标准中加一条非目标：Runtime 不自动改 Policy / Skill。另开 `eval` 与 `learning` 管道读事件、产候选 Skill，经人工或独立 reviewer 入库。现在就把进化做进 Loop，会违反「验证器不能自我修改」。

### P2-5. Coding Agent 延期，但 workspace 契约现在就要稳定

第五章认为文件系统是通用 Agent 的中枢。方案延期是正确的产品判断，但 `WorkspaceSpec`、Artifact、取消杀进程组应在 Phase 1 的协议里留稳定字段，避免 Phase 5 时改 Envelope。上游 Harness 文档已有 `.run/` 目录映射，Runtime 文档应显式引用，而不是只在 Phase 5 才出现容器。

### P2-6. 思考过程要进入可恢复轨迹

第一章消融：剥掉思考过程后前后决策会矛盾。`ModelEvent` 已有 `thinking.summary`。建议完整 thinking 按 Provider 策略入库（可对用户隐藏），恢复时按原 Turn 回放；若 Provider 不返回思考，标 `continuity` 时区分「缺思考」与「缺工具结果」。不要在恢复路径上把 thinking 当可丢字段。

## 7. 对实施路线的具体补丁

原 Phase 划分仍然合理，建议只加验收，不插新的大阶段。

**Phase 0**  
保留「无工具 Adapter + 现网行为不变」。增加：输入布局的静态前缀测试（改时间戳不得出现在 system 前缀）；最小评测集骨架；`provenance` 字段进入协议。

**Phase 1**  
保留崩溃恢复和不重复消息。增加：代码维护的状态栏（Turn、预算、工具计数）；流 idle watchdog；Turn 边界可注入排队中的用户消息；工具调用 / 结果完整性检查，缺配对则修复或失败，不把残缺轨迹喂给模型。

**Phase 2**  
保留审批和幂等账本。增加：Sidecar 仅结构化审查；`PROPOSED_COMPLETE` vs 控制面 `COMPLETED`；写工具的服务端真值校验；并行只读的故障隔离。验收补一条：提示注入不能让未授权写工具执行。

**Phase 3**  
保留压缩、Skill hash、MCP Gateway。验收从「快照可重建」改为「快照可重建，且默认只注入目录 / 索引，已加载集合可复现」。Skill 正文变化若不在已加载集合中，不得改变前缀 digest。

**Phase 4**  
保留 DAG 与多维配额。增加：Planner 在父预算内分配子预算；Aggregator 之后的独立验证节点（可先做确定性检查，再视任务加 Reviewer）。

**Phase 5**  
保持不变。协议侧提前冻结 `WorkspaceSpec` 与取消杀进程组语义。

**Phase 6（建议标明非目标 / 研究项）**  
离线从审计事件生成候选 Skill，独立验证后入库。不进入 Runtime Loop。

## 8. 总评

这份自建 Runtime 方案读起来不像「再写一个 LangChain」，而像本书所说的第三波工程：把模型放进有约束、可恢复、可审计的系统里。它最强的地方是承认了几件很多团队不愿承认的事：

- 模型输出不是权限
- 队列不是事实来源
- 流中断不是可续传的承诺
- 非幂等副作用在结果未知时必须停
- 多 Agent 不能藏在一次 Loop 里

这些都与《AI Agents in Depth》的生产叙事一致，也与 Pine / Claude Code 那条「可靠性倒逼 Harness」的经验同向。

它与本书的距离，主要不在模块图画得对不对，而在三件会决定智能上限和事故率的事还没写成协议：

1. **验证与完成权**仍在执行者手里  
2. **眼睛**还没有按静态前缀 + 按需披露 + 状态栏来长  
3. **评估**还没有成为改动的门禁  

补这三件，方案会从「可恢复的 Worker」变成书中意义上的生产级 Harness。不补也能做出比当前 `service.ts` 单次 completion 更稳的循环，但会在长任务、MCP 扩张和提示注入上重新支付书里已经写过的学费。
