# Smart Chat 自动重新部署指南

生产目标路径已经改为 GitHub Actions 构建镜像、服务器只拉取 GHCR SHA 标签。日常发版看 [GHCR 部署实施清单](GHCR部署实施清单.md)。

本页说明的 `scripts/redeploy.sh` / `make redeploy` 仍可用于应急：在服务器本地构建镜像。一旦 `/opt/smart-chat/.deploy/image.env` 存在，该脚本会拒绝执行，除非显式设置 `ALLOW_LOCAL_BUILD_REDEPLOY=1`。

## 1. 目的

本指南说明如何使用仓库内的 `scripts/redeploy.sh` 和 `Makefile` 更新已运行的 Docker 化 Smart Chat 服务。

自动重部署适用于以下生产拓扑：

```text
Caddy -> 127.0.0.1:3000 -> web 容器
                              -> postgres 容器
worker 容器 ------------------+
```

脚本不会执行 seed、删除数据卷或自动修改生产密钥。

## 2. 快速执行

在服务器项目目录运行：

```bash
cd /opt/smart-chat
make redeploy
```

等价命令：

```bash
./scripts/redeploy.sh
```

成功后会输出 `redeploy completed` 以及 PostgreSQL、Web、Worker 的容器状态。

## 3. 前置条件

- Docker 和 Docker Compose 已安装。
- 项目已经通过 Compose 部署过，或具备首次启动条件。
- `/opt/smart-chat/.env` 已配置。
- 当前用户可以运行 Docker。
- Git 远程仓库和当前分支可访问。
- PostgreSQL 数据卷可用。

`.env` 必须包含：

```env
POSTGRES_PASSWORD=数据库密码
SESSION_SECRET=至少32字符
AI_CONFIG_ENCRYPTION_KEY=至少32字符
AGENT_WORKER_SECRET=至少32字符
```

生产 `.env` 不应提交到 Git，文件权限建议为：

```bash
chmod 600 /opt/smart-chat/.env
```

## 4. 执行流程

```text
获取部署锁
  -> 检查 Git、Docker、Compose、.env
  -> 校验 Compose 配置
  -> 检查工作区是否干净
  -> git pull --ff-only
  -> 启动并等待 PostgreSQL
  -> pg_dump 数据库备份
  -> 构建新的 Web 镜像
  -> Prisma migrate deploy
  -> 重建 Web 和 Worker
  -> 轮询本地 Web 端口
  -> 验证三个容器均处于 running
```

脚本使用目录锁防止两次发布同时执行。异常退出时会释放锁。

### 4.1 拉取代码

使用：

```bash
git pull --ff-only
```

如果本地和远程分支产生分叉，命令会失败而不是自动 merge，避免在生产服务器生成未经审核的合并提交。

### 4.2 数据库备份

默认在迁移前执行 `pg_dump`，文件保存到：

```text
/opt/smart-chat/backups/smart-chat-YYYYMMDD-HHMMSS.sql
```

空备份会被视为部署失败。`backups/` 已加入 `.gitignore`。

### 4.3 镜像构建

新镜像构建完成前，现有 Web 容器继续运行。Docker Hub 或 npm 网络错误会终止发布，但不会主动停止现有容器。

### 4.4 数据库迁移

脚本执行：

```bash
docker compose run --rm web npx prisma migrate deploy
```

migration 失败时不会进入容器替换阶段。生产 migration 应保持向后兼容，因为数据库变更可能已经提交，而旧应用仍在运行。

### 4.5 容器替换和健康检查

迁移成功后执行：

```bash
docker compose --profile worker up -d --force-recreate postgres web worker
```

脚本从 Compose 获取 Web 的实际宿主机映射端口，每两秒发送一次 HTTP HEAD 请求。默认最多尝试 30 次，即等待 60 秒。

最后确认 `postgres`、`web`、`worker` 都处于 `running`。

## 5. 可选参数

### 不自动拉取代码

适用于已经手工完成 `git pull` 的情况：

```bash
AUTO_PULL=0 make redeploy
```

### 延长健康检查时间

最多等待 120 秒：

```bash
HEALTH_ATTEMPTS=60 make redeploy
```

### 修改备份目录

```bash
BACKUP_DIR=/var/backups/smart-chat make redeploy
```

确保执行用户对目录有写权限，并安排异机或对象存储备份。

### 跳过数据库备份

```bash
SKIP_BACKUP=1 make redeploy
```

生产环境不建议使用。只有外部备份系统已经完成同一发布点备份时才应跳过。

### 允许脏工作区

```bash
DEPLOY_ALLOW_DIRTY=1 make redeploy
```

这会允许服务器存在未提交的已跟踪文件修改。它可能导致服务器实际构建内容与 Git commit 不一致，应仅用于明确了解差异的应急场景。

## 6. 发布前检查

```bash
cd /opt/smart-chat
git status --short
docker compose config --quiet
docker compose --profile worker ps
df -h
```

发布前应确认工作区没有意外修改、Compose 配置有效、现有服务状态明确，并且磁盘有足够空间容纳新镜像和数据库备份。

## 7. 推荐发布 SOP

1. 确认目标 commit 已通过测试和代码审查。
2. 确认服务器磁盘空间和数据库健康。
3. 执行 `make redeploy`。
4. 检查脚本最终容器状态。
5. 检查 Web 和 Worker 最近日志。
6. 从公网验证 HTTPS 和登录跳转。
7. 登录后发送普通消息和 Agent 消息。
8. 记录 commit、备份文件和发布时间。

验证命令：

```bash
docker compose --profile worker ps
docker compose logs --tail=100 web
docker compose --profile worker logs --tail=100 worker
curl -IL https://43-130-52-92.sslip.io
```

## 8. 常见失败处理

### tracked files contain local changes

服务器存在未提交修改：

```bash
git status --short
git diff
```

检查差异后，应提交、暂存或恢复明确不需要的修改。不要在不清楚差异来源时直接使用 `DEPLOY_ALLOW_DIRTY=1`。

### git pull --ff-only 失败

检查：

```bash
git branch --show-current
git status
git log --oneline --decorate -10
```

生产服务器通常不应产生本地 commit。先确认分支和历史，再处理分叉。

### 数据库备份失败

```bash
docker compose ps postgres
docker compose logs --tail=100 postgres
df -h
```

确认 PostgreSQL healthy、磁盘空间足够、数据库用户名和数据卷正确。

### 镜像构建失败

```bash
docker compose build --no-cache web
```

检查 Docker Hub、npm 网络、磁盘空间和构建日志。构建失败不会主动停止旧 Web。

### migration 失败

```bash
docker compose run --rm web npx prisma migrate status
docker compose logs --tail=100 postgres
```

不要盲目删除 migration 或执行 `prisma db push`。根据失败 migration 和数据库状态制定修复方案。

### Web 健康检查失败

```bash
docker compose --profile worker ps
docker compose logs --tail=200 web
docker compose port web 3000
curl -Iv http://127.0.0.1:3000
```

重点检查环境变量、数据库连接、端口占用和 Next.js 启动错误。

### Worker 未运行或返回 401

```bash
docker compose --profile worker logs --tail=200 worker
```

确认 Web 与 Worker 读取的是同一个 `AGENT_WORKER_SECRET`。修改 `.env` 后必须重新创建容器。

## 9. 回滚原则

脚本不会自动执行数据库回滚。自动逆向 migration 容易造成数据损坏，生产数据库应优先使用向前修复。

应用回滚前需要确认：

- 新 migration 是否与旧应用兼容。
- 是否已经产生新格式数据。
- 回滚镜像或 commit 是否仍可读取当前 schema。
- 迁移前备份是否可用。

只回滚应用代码时，可以切换到已确认的 commit 后运行：

```bash
git checkout <已确认的commit>
AUTO_PULL=0 SKIP_BACKUP=1 make redeploy
```

该操作会改变服务器工作树，应在维护窗口执行并记录。恢复数据库备份属于破坏性操作，必须先停止写流量并单独制定恢复步骤。

## 10. 安全注意事项

- 不将 `.env`、`docker compose config` 完整输出或数据库备份上传到公开位置。
- 不对公网开放 3000、3011、5432。
- 不使用 `docker compose down -v`，它会删除命名卷。
- 不在部署脚本中自动 seed 生产数据库。
- 定期清理旧备份，但至少保留满足恢复目标的异机副本。
- `AI_CONFIG_ENCRYPTION_KEY` 必须备份；丢失后已有 Provider 密钥无法解密。
