# Smart Chat 产品需求文档

状态：Draft for implementation  
版本：0.1  
日期：2026-08-18

## 1. 产品目标

为小型团队和社区提供一个可自托管的多人实时文字聊天室。用户在同一房间内交流，并可显式 `@大聪明` 请求 AI 基于当前房间的有限上下文回答。系统管理员可在后台切换本地 AI 网关所连接的模型厂商和模型，同时保证房间权限、用户数据和密钥不泄露。

## 2. 用户与权限

| 能力 | 未登录访客 | 普通用户 | 系统管理员 |
| --- | --- | --- | --- |
| 查看公开房间目录 | 是 | 是 | 是 |
| 阅读房间消息 | 否 | 仅已加入房间 | 仅已加入房间 |
| 创建、加入、退出房间 | 否 | 是 | 是 |
| 发送文字、提及成员 | 否 | 是 | 是 |
| 修改自己的头像、昵称 | 否 | 是 | 是 |
| 管理 AI 厂商配置 | 否 | 否 | 是 |
| 查看配置变更审计 | 否 | 否 | 是 |

管理员不会因为角色而自动获得所有房间消息的读取权。

## 3. 核心用户故事

1. 新用户可使用邮箱和密码注册、登录、退出，并设置昵称和头像。
2. 任何访客可分页浏览和搜索公开聊天室；登录用户可创建或加入房间。
3. 创建房间时，创建者和“大聪明”成员必须在同一事务中加入房间。
4. 房间成员可实时发送和接收文字消息；断线重连后能按游标补齐消息且不重复。
5. 输入 `@` 时出现当前房间成员选择器，支持键盘选择与中文输入法。
6. `@普通成员` 不触发 AI；结构化提及“大聪明”时才创建一次 AI 请求。
7. AI 超时、限流或不可用时，原消息仍保留，并展示可重试的失败状态。
8. 管理员可配置厂商、模型、服务地址、超时和凭据，执行健康检查并查看审计；普通用户访问后台接口返回 403。

## 4. 功能需求

### 4.1 身份与资料

- 邮箱规范化并唯一；密码使用 Argon2id 哈希。
- Session 使用 `HttpOnly`、`Secure`、`SameSite=Lax` Cookie，支持主动退出和过期。
- 登录和注册错误不得泄露邮箱是否存在。
- 昵称有长度与字符约束；头像 V1 使用受控上传后的对象 key 或受信 URL，不允许服务端抓取任意远程 URL。
- 系统角色为 `USER`、`ADMIN`，服务端对每个受保护动作重新鉴权。

### 4.2 房间与成员

- 房间目录公开，支持游标分页、名称搜索、最近活跃排序。
- V1 房间均为 `PUBLIC/ACTIVE`；数据模型预留 private、archived、invite-only。
- 登录用户可创建、加入和退出房间；重复加入必须幂等。
- 非成员不得读取消息、订阅实时频道或发送消息。
- “大聪明”为不可删除的 `ASSISTANT` 类型房间成员。

### 4.3 文字消息与提及

- V1 仅接受 `text` 内容，限制长度并拒绝不受支持的 content part。
- 每条发送命令带 `clientId`，服务端按 `(roomId, senderMemberId, clientId)` 去重，并分配单调递增的房间 sequence。退出后旧 membership 不可复用；旧命令重试被拒绝，重新加入产生新的 membership epoch。
- 消息分页使用游标；重连从最后确认 sequence 补齐。
- 客户端 mention picker 只用于交互；服务端验证 mention 指向当前 active member。
- mention 以结构化关联保存，不能只依赖正文中的 `@` 字符串。

### 4.4 AI 助手

- 只有结构化 mention 指向“大聪明”时才触发 AI。
- 上下文只来自同一房间、调用用户有权读取的最近消息，并受消息条数和 token budget 双重限制。
- 用户消息先持久化，再异步创建 AI run；AI 失败不得回滚用户消息。
- AI 回复作为独立消息持久化并广播；每个触发消息最多产生一个有效 AI run。
- AI 网关采用服务端适配器，优先支持 OpenAI-compatible 协议；provider/model/base URL/timeout 可配置。
- Provider 密钥只写不可读，不返回浏览器、不写日志、不进入模型上下文。

### 4.5 管理后台

- 管理员可查看脱敏配置、更新非敏感项、轮换密钥、启停配置和执行健康检查。
- 配置变更记录 actor、时间、前后版本、操作类型和结果，但不记录明文密钥。
- 管理员可在 `/admin/audit` 按 actor/action/time 游标分页查看脱敏审计；普通用户访问页面或 API 均返回 403。
- Base URL 必须满足 allowlist/出站策略，防止 SSRF；本地网关地址需显式允许。

## 5. 非功能需求

- 安全：服务端权限校验、CSRF/origin 校验、XSS 输出编码、速率限制、安全响应头、IDOR/SSRF 防护、日志脱敏。
- 可靠性：消息与 outbox 同事务写入；消费者幂等；断线可重放；AI worker 有超时和有界重试。
- 性能基线：不含 AI 的 API P95 < 300ms；消息广播 P95 < 1s；最终指标在容量评审后确认。
- 可观测性：request/correlation ID、AI run ID、结构化日志、消息延迟/连接数/AI 错误率/outbox backlog 指标，禁止记录消息正文和凭据。
- 可访问性：mention picker 可用键盘操作并提供 ARIA，消息流有适当的 live region，移动端可用。
- 演进性：消息保留 `contentParts` 版本化字段，但 V1 API 拒绝非文字 part；图片上传与审核不在 V1。

## 6. 明确不在 V1 的范围

- 图片、文件、语音、富文本和 Markdown。
- 私密房间、邀请制、消息编辑/撤回、已读回执、输入中状态。
- 第三方 OAuth、Passkey、找回密码、邮箱验证、管理员 MFA。
- 多 AI 角色、自动响应所有消息、跨房间知识检索。

以上能力是后续候选，并非承诺；其中找回密码、邮箱验证和管理员 MFA 应在公网生产发布前重新评审。

## 7. 验收标准

- AC-01：注册、登录、退出和 session 过期链路可用，数据库不存明文密码，错误不暴露账号存在性。
- AC-02：访客可看目录但读消息返回 401；非成员读写或订阅房间返回 403/404 且无数据泄露。
- AC-03：房间、创建者 membership 和 AI membership 原子创建；重复加入不产生重复记录。
- AC-04：同一 `clientId` 重试只生成一条消息；在线成员收到相同 sequence，重连可补齐无重复。
- AC-05：mention picker 仅列 active members；伪造 mention 被拒绝；提及普通用户不调用 AI。
- AC-06：每次有效 `@大聪明` 只生成一个 AI run；payload 不含其他房间内容或密钥；成功/失败状态均落库并可观察。
- AC-07：普通用户的所有 admin API 均为 403；管理员可更新/检查配置；GET、日志和客户端 bundle 中无凭据。
- AC-08：XSS、CSRF、IDOR、SSRF、暴力登录和消息/AI 限流测试通过。
- AC-09：V1 只接受文字 part；未知 part 被拒绝；现有读取模型可在未来增加 image part 而无需重写文字消息。
- AC-10：访客目录分页、搜索、公开/活跃过滤和最近活跃排序稳定，响应不泄露成员或消息；用户只能更新自己的资料。
- AC-11：冻结的 SLO 在规定负载与样本窗口下通过自动断言；未冻结时不得宣称满足生产容量。

## 8. 开放决策

实施前硬门禁：确认消息留存/删除/导出规则、目标并发量、部署环境的长连接能力、本地 AI 网关协议及凭据保管方式；这些决定影响 schema、容量和安全边界，未冻结不得进入 Phase 1。

公网生产发布门禁：明确邮箱验证/CAPTCHA、管理员 MFA、隐私声明与备份 RPO/RTO。开发环境的默认值为不启用邮箱验证/CAPTCHA/MFA，消息保留 30 天且仅支持管理员运维删除；这些默认值不得被解释为生产决策。
